# Доступные варианты поиска TeamCity

- Статус: реализовано и проверено для версии 1.4.0
- Целевая версия: 1.4.0 (`MINOR`)
- Область: Browser Extension
- Последнее обновление: 2026-08-25

Связанные документы:

- [PRODUCT.md](PRODUCT.md) — продуктовые правила;
- [ARCHITECTURE.md](ARCHITECTURE.md) — архитектурные границы расширения;
- [TEAMCITY_INTEGRATION.md](TEAMCITY_INTEGRATION.md) — текущий TeamCity REST-контракт;
- [FEATURE_MATRIX.md](FEATURE_MATRIX.md) — подтверждённое пользовательское поведение.

## 1. Назначение

Документ фиксирует требования к доступным вариантам поиска по ветке задачи и номеру билда в TeamCity Mobile Build Assistant.

Новый функционал расширяет существующее поле поиска:

- пользователь по-прежнему может вводить произвольный текст;
- текущий TeamCity-поиск сборок не меняет семантику;
- после выбора проекта extension загружает доступные поисковые значения;
- значения отображаются в том же dropdown, где находится история поиска;
- окружения и платформы фильтруют уже загруженные данные локально;
- история поиска остаётся отдельным источником значений.

Документ является источником требований для реализации, regression tests, ручной проверки и последующего обновления README.

## 2. Границы версии 1.4.0

### 2.1. Входит в scope

- Доступные номера билдов выбранного проекта.
- Извлечённые идентификаторы задач из логических имён веток выбранного проекта.
- Один выбранный проект одновременно.
- Несколько одновременно выбранных окружений.
- Несколько одновременно выбранных платформ.
- Два источника значений в dropdown: `Текущие данные` и `История поиска`.
- Прогрессивная загрузка TeamCity build metadata без поиска артефактов.
- Refresh, Stop, partial result, empty и error states.
- Ограниченный session cache.
- Сохранение поискового запроса в историю сразу после запуска основного поиска.

### 2.2. Не входит в scope

- Одновременный выбор нескольких проектов.
- Изменение серверной семантики существующего поиска сборок.
- Предварительный поиск APK/IPA для заполнения dropdown.
- Отдельный UI-flow управления правами TeamCity.
- Отображение failed, running, canceled или personal builds в доступных вариантах.
- Хранение полного TeamCity response body.
- Постоянный кэш доступных значений в `chrome.storage.local`.
- Пользовательская настройка шаблона извлечения task ID в UI версии 1.4.0.

## 3. Источник данных

### 3.1. Каталог

При открытии ассистента сохраняется существующий flow:

1. Проверить текущую TeamCity browser-session.
2. Загрузить доступные текущему пользователю build configurations.
3. Построить список проектов.
4. Классифицировать конфигурации по платформе и окружению.

Проект имеет ту же семантику, что и существующее значение в dropdown проектов. Новая функция не меняет текущую модель вложенных TeamCity-проектов.

### 3.2. Момент загрузки

До выбора проекта build metadata не запрашиваются.

После выбора проекта автоматически начинается загрузка доступных значений по всем неприостановленным конфигурациям этого проекта. Переключение на другой проект:

- останавливает активную загрузку предыдущего проекта;
- очищает оба draft-query: поиск по задаче и поиск по номеру билда;
- активирует чип `Текущие данные`;
- запускает загрузку или использует допустимый session cache нового проекта.

### 3.3. TeamCity builds

Область доступных вариантов должна совпадать с областью существующего поиска:

```text
state:finished
status:SUCCESS
branch:default:any
неприостановленные build configurations выбранного проекта
```

Минимальная build-модель:

```text
id
buildTypeId
number
branchName?
defaultBranch
unspecifiedBranch?
finishDate?
```

Основной REST endpoint:

```text
GET /app/rest/builds
```

Locator объединяет подходящие `buildTypeId`, а `fields` ограничиваются полями, необходимыми для индекса. Pagination выполняется только по server-provided `nextHref`.

Если список `buildTypeId` создаёт чрезмерно длинный locator, конфигурации делятся на ограниченные chunks. Количество одновременно выполняемых chunks должно быть bounded.

Artifact endpoints при построении доступных вариантов не вызываются.

## 4. Модель выбранных фильтров

Одновременно выбран только один проект:

```text
selectedProjectId: string | empty
```

Окружения и платформы являются множественным выбором:

```text
selectedEnvironments: Set<MobileEnvironment>
selectedPlatforms: Set<AssistantPlatformFilter>
```

Фильтрация конфигураций:

```text
configuration.projectId == selectedProjectId
AND
(
  selectedEnvironments пуст
  OR configuration.environment входит в selectedEnvironments
)
AND
(
  selectedPlatforms пуст
  OR configuration.platform входит в selectedPlatforms
)
```

Правила:

- внутри списка окружений действует `OR`;
- внутри списка платформ действует `OR`;
- между проектом, окружениями и платформами действует `AND`;
- пустой выбор окружений означает все окружения;
- пустой выбор платформ означает все платформы;
- без выбранного проекта основной поиск и доступные текущие данные недоступны.

Изменение окружений или платформ немедленно пересчитывает видимые `Текущие данные` по уже загруженному индексу, даже если dropdown открыт.

Если введённое значение перестало соответствовать фильтрам, оно сохраняется как свободный текст.

## 5. Режимы поиска

Существующие режимы сохраняются:

- `task` — поиск по части branch name;
- `build` — поиск по точному публичному build number.

Один metadata index используется для обоих режимов. Переключение режима:

- не запускает повторный TeamCity-запрос;
- переключает набор отображаемых значений;
- всегда активирует чип `Текущие данные`;
- сохраняет раздельные draft-query режимов до смены проекта;
- сохраняет раздельную историю режимов.

Клик по доступному или историческому значению только подставляет текст в input. Поиск автоматически не запускается. После подстановки применяется существующая семантика ручного ввода:

- task query остаётся частичным `contains`-поиском;
- build number query остаётся существующим точным поиском.

## 6. Извлечение идентификатора задачи

TeamCity возвращает логическое имя ветки, но не универсальный task ID. В версии 1.4.0 применяется отдельный `TaskIdentifierExtractor` с общей безопасной эвристикой.

### 6.1. Приоритет 1: буквенно-цифровой ключ

Из branch name извлекается первое значение вида:

```text
<буквенно-цифровой префикс>-<цифры>
```

Синтетические примеры:

```text
feature/TEST-1111             -> TEST-1111
bugfix/mobile-42-title        -> mobile-42
feature/TEST-1111-description -> TEST-1111
```

### 6.2. Приоритет 2: числовая задача

Если буквенно-цифровой ключ отсутствует, допускается числовой идентификатор в распространённых task-ветках, например `feature`, `bugfix`, `fix`, `task`, `hotfix`, `issue` или `ticket`:

```text
feature/4233       -> 4233
bugfix/2215-title  -> 2215
task/1111          -> 1111
```

Числа из произвольных release/version branches не должны автоматически считаться задачами.

### 6.3. Неоднозначность и отсутствие значения

- Если найдено несколько подходящих task ID, используется первое слева.
- Если task ID безопасно не извлечён, branch не включается в `Текущие данные` режима задач.
- Ветка остаётся доступной через существующий ручной `contains`-поиск.
- Default и unspecified branches без извлечённого task ID не отображаются как задачи.

### 6.4. Регистр и дедупликация

- Task ID дедуплицируются без учёта регистра.
- Отображается первое написание, встретившееся в порядке ответа TeamCity.
- Build numbers считаются opaque strings и дедуплицируются по полному значению.
- Одинаковое значение из нескольких конфигураций отображается одной строкой.

## 7. Порядок и ограничение выдачи

Доступные значения сохраняют порядок первого появления в paginated-ответах TeamCity.

Dropdown показывает не более 50 совпадений текущего режима и текущих локальных фильтров:

- silent truncation допустим;
- отдельная строка `Уточните запрос` не показывается;
- input фильтрует весь уже загруженный индекс;
- после изменения input первые 50 совпадений вычисляются заново;
- одновременно видимая область рассчитана на пять строк;
- существующий scrollbar используется для остальных строк в пределах 50 значений.

Ограничение в 50 строк относится к визуальной выдаче, а не к объёму обрабатываемой TeamCity pagination.

## 8. Структура dropdown

Существующая строка с кнопкой `Очистить` удаляется. Первая строка dropdown делится на два кликабельных чипа:

1. `Текущие данные`.
2. `История поиска`.

### 8.1. Общие правила чипов

- По умолчанию активен `Текущие данные`.
- Клик по основной области чипа только переключает источник списка.
- Внутренняя action-кнопка доступна только у активного чипа.
- Action-кнопка неактивного чипа disabled, не нажимается и не имеет hover-state.
- После переключения режима поиска активируется `Текущие данные`.
- После переключения проекта активируется `Текущие данные`.

### 8.2. Чип `Текущие данные`

Внутренняя кнопка:

- в обычном состоянии — Refresh;
- во время загрузки — существующая иконка Stop;
- после завершения, остановки или ошибки — снова Refresh.

Refresh не переключает режим и обновляет только build configurations, соответствующие текущим Environment/Platform-фильтрам. Если окружения или платформы не выбраны, обновляются все неприостановленные конфигурации проекта.

### 8.3. Чип `История поиска`

Внутренняя кнопка очищает только историю активного режима поиска.

После очистки:

- активируется `Текущие данные`;
- история другого режима не меняется;
- пустой history-чип остаётся видимым и переключаемым.

## 9. Открытие и закрытие dropdown

Dropdown открывается по focus или click на input независимо от наличия текущих данных или истории.

Закрытие по внешнему click, Escape или другому существующему UI-действию:

- закрывает dropdown;
- останавливает активную загрузку доступных данных;
- сохраняет уже найденные partial results;
- не продолжает загрузку автоматически при повторном открытии.

При повторном открытии показывается сохранённый частичный список. Продолжение возможно только после нажатия Refresh. Refresh начинает новое обновление текущего набора конфигураций.

## 10. Прогрессивная загрузка

Данные публикуются после каждой успешно разобранной страницы TeamCity.

Пока загрузка продолжается, нижняя пятая строка зарезервирована под loader:

```text
строка 1 — результат
строка 2 — результат
строка 3 — результат
строка 4 — результат
строка 5 — loader
```

После завершения загрузки пятая строка снова доступна для результата.

Если результатов ещё нет, loader занимает нижнюю зарезервированную строку пустого списка. Полноэкранный loader из переходного макета не должен блокировать остальные контролы после появления первых данных.

Во время загрузки блокируются dropdown и его внутренние action-кнопки в пределах, необходимых для предотвращения конфликтующих действий. Проект, окружения, платформы и основная кнопка поиска не блокируются новой загрузкой доступных значений.

Stop:

- останавливает только metadata-загрузку доступных значений;
- не останавливает основной поиск сборок;
- сохраняет опубликованные значения;
- оставляет dropdown открытым;
- возвращает иконку Refresh.

## 11. Изменение фильтров во время загрузки

Если пользователь меняет Environment или Platform во время manual Refresh:

1. Активный Refresh останавливается на текущем прогрессе.
2. Уже загруженные данные сохраняются.
3. Список немедленно локально пересчитывается по новым фильтрам.
4. Автоматический новый TeamCity-запрос не запускается.
5. Пользователь может нажать Refresh, если частичного результата недостаточно.

Смена проекта всегда останавливает старую загрузку и запускает project-selection flow нового проекта.

## 12. Empty, partial и error states

### 12.1. Нет данных

Если активный источник не содержит значений, внутри списка показывается:

```text
НЕТ ДАННЫХ
```

Правила:

- пустые текущие данные не переключают UI на историю автоматически;
- пустая история не переключает UI на текущие данные автоматически;
- `Текущие данные` остаются источником по умолчанию;
- history-чип остаётся переключаемым даже при пустой истории.

### 12.2. Частичные данные

Частичные данные допустимы после Stop, закрытия dropdown, смены фильтров или частично завершённой pagination. Они отображаются как обычные строки. Автоматического фонового продолжения после остановки нет.

### 12.3. Ошибка

При ошибке текущего Refresh:

- прежний список текущего обновляемого scope не восстанавливается;
- вместо `НЕТ ДАННЫХ` показывается существующее безопасное пользовательское сообщение ошибки;
- raw TeamCity URL, response body и internal diagnostics не показываются;
- отдельный UI-flow для 403 не добавляется;
- после ошибки внутренняя кнопка снова становится Refresh.

Используются существующие категории сообщений:

- требуется авторизация;
- доступ запрещён;
- ответ слишком большой;
- превышено ограничение обхода;
- timeout;
- TeamCity недоступен;
- неизвестный формат ответа.

## 13. История поиска

История сохраняет введённые query, а не найденные карточки сборок.

Правила остаются общими для TeamCity origin:

- отдельная история для `task`;
- отдельная история для `build`;
- максимум пять непустых значений на режим;
- повторное значение перемещается в начало;
- выбор значения восстанавливает только текст;
- проекты, окружения и платформы не сохраняются в записи истории;
- input не фильтрует историю;
- пятая запись при необходимости доступна через существующий scrollbar.

Изменение относительно текущей реализации:

- непустой query добавляется в историю сразу после нажатия `Поиск сборок`;
- сохранение выполняется до результата TeamCity;
- query остаётся в истории при пустом результате, ошибке или остановке поиска;
- пустой query в историю не добавляется.

Корзина очищает только историю текущего режима. После очистки активируется `Текущие данные`.

## 14. Session cache

Кэш нужен для быстрого повторного переключения между проектами, но не должен неограниченно расти или переживать смену TeamCity-пользователя.

### 14.1. Scope ключа

```text
TeamCity origin
+ authenticated user cache scope
+ projectId
```

### 14.2. Хранение

- Только в памяти browser-session.
- Не использовать `chrome.storage.local` для доступных TeamCity-значений.
- Не сохранять raw responses.
- Хранить агрегированные значения по build configuration.
- Временные build IDs и pagination state хранить только пока они нужны для активной загрузки или безопасного Stop.

### 14.3. Ограничения

- Не более трёх недавно использованных project-indexes.
- LRU-удаление четвёртого проекта.
- Idle TTL одного project-index — 10 минут.
- Просроченные entries удаляются лениво при следующем обращении и периодической очисткой session cache.

### 14.4. Инвалидация

Project-index удаляется или заменяется при:

- смене TeamCity origin;
- смене authenticated user cache scope;
- 401 или 403;
- обновлении каталога, изменившем набор/классификацию конфигураций проекта;
- истечении TTL;
- LRU eviction.

Manual Refresh заменяет данные только конфигураций текущего фильтрованного scope и не раздувает project-index дубликатами.

## 15. Конкурентность и безопасность

- Для каждой project-selection/manual-refresh операции используется отдельный `AbortController`.
- Новая несовместимая операция отменяет предыдущую.
- `nextHref` принимается только через существующую same-origin REST-валидацию.
- Повторяющийся `nextHref` считается ошибкой обхода.
- Page size, maximum pages, request timeout, общий operation timeout и chunk concurrency должны быть bounded.
- UI получает данные только через нормализованную доменную модель.
- Реальные TeamCity identifiers, branches, numbers и response bodies не добавляются в source, tests или документацию.
- Regression tests используют только синтетические значения и домены `example.test`/`example.invalid`.

## 16. Сохранение существующего поведения

Новый функционал не должен менять:

- TeamCity branch `contains` locator основного task-поиска;
- точный locator основного поиска по build number;
- фильтрацию основного поиска по проекту, окружению и платформе;
- прогрессивное отображение карточек найденных артефактов;
- Stop основного поиска сборок;
- artifact resolution;
- карточки результатов и пояснения конфигурации/платформы/окружения;
- безопасность TeamCity transport.

Stop внутри чипа `Текущие данные` и Stop основного поиска являются разными операциями и имеют независимые `AbortController`.

## 17. Ожидаемые автоматические проверки

### 17.1. TeamCity index

- Используются только `SUCCESS + finished` builds всех веток.
- Приостановленные конфигурации исключены.
- Несколько конфигураций объединяются или безопасно chunk-ятся.
- `nextHref` обрабатывается прогрессивно.
- Repeated pagination link останавливается.
- Stop сохраняет опубликованный partial result.
- Смена проекта отменяет предыдущую загрузку.
- Смена фильтров останавливает manual Refresh без потери прогресса.
- Artifact endpoints не вызываются.
- Error заменяет текущий список безопасным сообщением.

### 17.2. Task ID extractor

- Буквенно-цифровой task ID.
- Числовой task ID в поддерживаемом branch prefix.
- Несколько task ID — выбран первый.
- Case-insensitive deduplication.
- Default/unspecified branch без task ID исключён.
- Release/version number не принят за numeric task ID.

### 17.3. Локальные фильтры

- Один/несколько environments.
- Одна/несколько platforms.
- Пустое измерение означает все значения.
- Между dimensions применяется `AND`.
- Изменение фильтров пересчитывает открытый dropdown.
- Свободный текст сохраняется, даже если исчез из текущих вариантов.

### 17.4. Dropdown

- Открывается при пустых источниках.
- По умолчанию активны `Текущие данные`.
- Mode/project switch возвращает `Текущие данные`.
- Неактивные action-кнопки disabled и без hover.
- Refresh меняется на Stop и обратно.
- Четыре результата плюс loader во время загрузки.
- Пять строк после завершения.
- Не более 50 текущих совпадений.
- Клик по строке только заполняет input.
- Закрытие dropdown останавливает загрузку.
- Повторное открытие не продолжает её автоматически.

### 17.5. История

- Query сохраняется сразу после запуска поиска.
- Сохраняется при error, empty и Stop.
- Пустое значение не сохраняется.
- Максимум пять значений на режим.
- Режимы имеют независимые истории.
- Корзина очищает только активный режим.
- После очистки активируются `Текущие данные`.
- История не фильтруется input.

### 17.6. Cache

- Ключ учитывает origin/user/project.
- TTL удаляет неактивный индекс.
- LRU ограничивает число проектов тремя.
- Смена пользователя не показывает данные предыдущего пользователя.
- Refresh заменяет scope без накопления дубликатов.

## 18. Ручная проверка

Перед выпуском необходимы синтетическая/локальная и авторизованная read-only проверки:

1. Первый выбор проекта и прогрессивное появление значений.
2. Переключение задач и номеров билдов без повторной загрузки.
3. Несколько окружений и платформ в разных комбинациях.
4. Ввод, сокращающий список до нужного значения.
5. Silent limit 50 и scrollbar пятистрочного viewport.
6. Refresh, Stop и сохранённый partial result.
7. Закрытие dropdown во время загрузки.
8. Повторное открытие без автоматического продолжения.
9. Ошибка TeamCity вместо `НЕТ ДАННЫХ`.
10. Очистка истории активного режима.
11. Смена проекта и очистка обоих query.
12. Отсутствие artifact-запросов до запуска основного поиска.

Реальные диагностические данные после ручной проверки не сохраняются.

## 19. План обновления README после реализации

README обновляется только после фактической реализации и проверки поведения. Нужно будет отразить:

- автоматическую загрузку доступных задач и номеров билдов после выбора проекта;
- локальную фильтрацию по нескольким окружениям и платформам;
- переключение `Текущие данные` / `История поиска`;
- Refresh и Stop загрузки вариантов;
- progressive/partial/error states;
- лимит визуальной выдачи и уточнение через input;
- сохранение query в историю независимо от результата поиска;
- privacy-границы session cache;
- актуальные screenshots, если внешний вид README должен соответствовать версии 1.4.0;
- новую строку/раздел в `FEATURE_MATRIX.md`;
- актуализацию `TEAMCITY_INTEGRATION.md`, если итоговый REST-контракт отличается от документа.

README не должен обещать абсолютную универсальность извлечения task ID. Формулировка должна указывать на поддержку распространённых branch naming conventions и сохранение ручного поиска как fallback.

## 20. Критерии готовности

Функция считается готовой, когда:

1. Все обязательные состояния макетов реализованы для обоих режимов поиска.
2. Доступные значения загружаются только после выбора проекта.
3. Текущие значения соответствуют области основного поиска.
4. Environment/Platform-фильтры работают локально и поддерживают множественный выбор.
5. Progressive loading, Refresh, Stop, close-abort, partial и error states проверены.
6. История соответствует новому моменту сохранения и правилам очистки.
7. Cache bounded и не переносит данные между пользователями.
8. Все новые TeamCity response contracts покрыты синтетическими tests.
9. Полный набор проверок проекта и public safety scan успешен.
10. README и связанные документы обновлены по фактически реализованному поведению.
