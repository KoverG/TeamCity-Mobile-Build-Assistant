## 1. Назначение продукта

TeamCity Mobile Build Assistant сокращает количество действий, необходимых сотруднику для поиска и получения мобильной сборки.

Пользователь работает в уже открытой и авторизованной вкладке TeamCity. Browser Extension встраивает в страницу собственную панель, помогает выбрать нужную сборку, находит APK или IPA в artifacts и позволяет скопировать или открыть защищённую TeamCity-ссылку.

Главные продуктовые принципы:

1. Минимум лишних переходов и кликов.
2. Пользователь выбирает Project и при необходимости уточняет Platform и Environment; подходящие builds определяются ограниченным поиском.
3. Продукт не выбирает «самую актуальную сборку» и ничего не отправляет автоматически.
4. TeamCity остаётся источником авторизации и прав доступа к builds и artifacts.
5. TeamCity credentials и browser-session data не покидают браузер и не попадают в код Browser Extension.
6. Поиск ориентирован на конечный APK/IPA, а не на фиксированную структуру каталогов или `.nupkg`.
7. Дополнительные действия подключаются через единый frontend-сервис и не изменяют базовый TeamCity-сценарий.
8. Продукт разрабатывается как публичный open-source-проект и не зависит от конкретной компании, TeamCity-доменов, project IDs или соглашений об именовании.
9. Данные реальной компании и её TeamCity-инсталляции не должны попадать в исходный код, конфигурацию по умолчанию, tests, fixtures, документацию, logs или историю Git.

Open-source-безопасность является обязательным продуктовым ограничением. Функция не считается готовой, если для её работы нужно зафиксировать в repository реальный URL, имя проекта, идентификатор build configuration, branch, artifact path либо другой tenant-specific параметр. Такие данные обнаруживаются во время работы или задаются пользователем во внешней локальной конфигурации.

## 2. Пользователи и предпосылки

MVP предназначен для небольшой группы сотрудников, которым уже предоставлен доступ к нужным проектам TeamCity.

Пользователь должен:

- быть авторизован в TeamCity в браузере, где установлено расширение;
- иметь доступ к выбранным projects, builds и artifacts.

Продукт не создаёт отдельные логины и пароли и не участвует в TeamCity authentication flow.

## 3. Клиентский интерфейс

### 3.1. Формат клиента

MVP — Browser Extension для Chromium-браузеров:

- Google Chrome;
- Microsoft Edge;
- Яндекс Браузер.

Расширение работает внутри страницы TeamCity. Перемещаемый хлястик изначально закрепляется у правой границы левой навигации TeamCity и открывает встроенную панель. Пользователь может перемещать хлястик по вертикали только за выделенный вертикальный хват, переносить его к правой границе контентного viewport перед вертикальной полосой прокрутки и сворачивать с плавной анимацией до самого хвата. Небольшое горизонтальное отклонение во время вертикального drag-жеста игнорируется: открепление начинается после смещения на ширину раскрытого хлястика, а выбор стороны происходит только при отпускании за серединой контентного viewport. Положение, сторона и compact-состояние сохраняются локально для текущего TeamCity origin. Отдельный сайт в MVP не нужен.

### 3.2. Основной выбор

Панель содержит фильтры поиска:

```text
Project → Search query? → Environment? → Platform? → Search builds
```

Текстовый запрос необязателен: пустое значение сохраняет поиск последних сборок. Переключатель выбирает один из двух режимов:

- по номеру задачи — регистронезависимое частичное совпадение внутри имени branch;
- по публичному `build.number` — точное совпадение номера.

В открытой рабочей сессии для режимов поддерживаются раздельные незавершённые значения. Раздельная история из пяти уникальных запросов, newest-first, хранится локально отдельно для каждого TeamCity origin, пополняется после успешно завершённого запроса, включая пустой результат, и не пополняется после ошибки сети.

Поддерживаемые платформы:

- Android;
- iOS.

Поддерживаемые environments:

- Development;
- Staging;
- Preview;
- PreProduction;
- Production.

Project и build configurations загружаются динамически из TeamCity REST API в пределах прав текущего пользователя. OS и Environment определяются отдельным классификатором build configurations.

Project обязателен. Platform и Environment необязательны:

- если не выбрана ни одна платформа, поиск выполняется по Android и iOS;
- выбор обеих платформ эквивалентен пустому выбору;
- пустой Environment означает поиск по всем распознанным environments;
- при изменении Platform выбранный Environment сбрасывается;
- кнопки Android и iOS занимают по половине доступной ширины; отдельной кнопки `Все` нет.

### 3.3. Выбор build

После команды `Поиск сборок` Extension проверяет не более 20 последних builds суммарно. Одновременно выполняется не более четырёх поисков artifacts. Исходные builds должны удовлетворять условиям:

- `status:SUCCESS`;
- `state:finished`;
- build относится к build configuration, соответствующей выбранным фильтрам;
- учитываются все доступные branches.

В результат попадают только builds, для которых найден ровно один APK или IPA. `NotFound`, `Ambiguous` и ошибка отдельного build не создают карточку результата. Для карточки отображаются:

- публичный номер;
- имя build configuration;
- branch;
- дата завершения;
- размер artifact в MB либо `—`, если TeamCity не вернул размер.

Пользователь может:

- выбрать одну или несколько карточек;
- открыть страницу build в новой фоновой вкладке TeamCity кликом по его публичному номеру, не покидая текущую вкладку;
- скопировать ссылку отдельного build, всех результатов или выбранных результатов;
- скачать artifact отдельного build через действие, раскрываемое ПКМ или клавиатурным контекстным меню;
- изменить сортировку результатов: сначала новые или сначала старые.

Результаты отображаются в отдельной панели 342×450 px, которая выезжает из-под основной панели без зазора. Красный хлястик результатов доступен сразу после открытия основной панели; поиск раскрывает результаты автоматически. До первого поиска показывается начальное состояние, во время запроса — анимированный маскот, loader и кнопка остановки, после пустого ответа или ручной остановки без результатов — отдельное состояние «не найдено». Ошибка поиска показывается без маскота и содержит кнопку повторения.

### 3.4. Жизненный цикл рабочей сессии

Пока панель открыта, она сохраняет текущие фильтры, запрос, результаты и выбранные карточки. Закрытие панели начинает новую чистую рабочую сессию: сбрасываются Project, Platform, Environment, черновики, результаты, выбранные карточки и положение панели результатов. Между сессиями сохраняется только история из пяти запросов для каждого режима и TeamCity origin.

Если панель закрыта во время поиска, активный запрос и его состояние не сбрасываются. Пользователь может открыть панель снова и продолжить наблюдение. Если поиск завершился или прервался, пока панель остаётся закрытой, рабочая сессия сбрасывается автоматически. Регистрация на backend для этого не нужна.

### 3.5. Onboarding

При первом запуске показывается обязательное уведомление:

> Для получения списка и скачивания сборок необходимо войти в TeamCity в используемом браузере.

Пользователь подтверждает:

> Я понимаю, что ссылки защищены авторизацией TeamCity.

Принятие сохраняется вместе с версией текста. При изменении существенных условий версия увеличивается, и уведомление показывается повторно.

## 4. Состояния TeamCity-сессии

Extension не выполняет вход в TeamCity.

Если REST API недоступен из-за отсутствующей или истёкшей сессии, UI показывает отдельное состояние с понятным действием:

> Авторизуйтесь в TeamCity и повторите запрос.

Технический adapter должен различать как минимум:

- HTTP `401/403`;
- redirect на login page;
- HTML login page вместо ожидаемого JSON/XML;
- сетевую ошибку;
- timeout;
- недостаток прав на конкретный project/build/artifact.

## 5. Поиск APK/IPA

Поиск artifacts автоматически выполняется для ограниченного списка подходящих builds после нажатия `Поиск сборок`.

Правила:

- для Android целевой файл — `.apk`;
- для iOS целевой файл — `.ipa`;
- основной поиск использует bulk listing TeamCity и получает список файлов минимальным количеством GET-запросов;
- расширение фильтрует `.apk`/`.ipa` без учёта регистра и использует выданный TeamCity `contentHref`; если поле отсутствует, применяется проверенный runtime fallback `repository/download`;
- если bulk listing конкретной версии TeamCity не раскрывает archive/container nodes, запускается ограниченный по времени, глубине, количеству запросов и параллелизму fallback traversal;
- поддерживаются обычные директории и раскрываемые TeamCity archive/container nodes;
- структура каталогов заранее не предполагается;
- `.nupkg` не считается конечным результатом и является лишь одним из возможных контейнеров.

Результат поиска одного build:

| Количество кандидатов | Поведение |
|---|---|
| 0 | Build не добавляется в результаты |
| 1 | Build добавляется в результаты |
| 2 и более | Build не добавляется в результаты |

Автоматически выбирать один файл среди нескольких запрещено.

## 6. Действия с найденным artifact

Для однозначно найденного APK/IPA доступны:

- скопировать прямую защищённую TeamCity-ссылку;
- открыть/скачать artifact;
- выбрать карточку для группового действия.

Меню настроек и тёмная тема остаются декоративными заглушками: при клике внешнее действие не выполняется. Светлая тема используется всегда.

Ссылка использует TeamCity `repository/download` и остаётся защищённой TeamCity authentication. Backend не проксирует и не скачивает файл в MVP.

Artifacts могут быть удалены TeamCity cleanup policy. Поэтому сохранённая ранее ссылка не гарантируется как вечная. Продукт не копирует artifacts в собственное хранилище.

## 7. Дополнительные действия

Базовая версия не зависит от собственного backend и не выполняет внешние действия. Поиск, выбор, копирование, скачивание и открытие сборок работают только через текущую TeamCity-сессию пользователя.

Для будущих Telegram-функций предусмотрены универсальные точки расширения:

- компактные действия в панели настроек;
- действия над выбранными результатами поиска;
- единый `AdditionalActionsService` для загрузки и выполнения действий;
- локальный allowlist иконок и мест отображения;
- пустой gateway по умолчанию, который не выполняет сетевых запросов.

Telegram-интеграция подключает один gateway к центральному сервису. UI-слоты не знают адресов API и не содержат интеграционной логики. Ошибка или отсутствие gateway не влияет на базовые функции и не оставляет в интерфейсе пустых областей. Универсальный механизм не предназначен для добавления других серверных интеграций.

## 8. Scope версии 1.2.0

В первую итерацию нового дизайна входят:

- установка Extension в режиме разработчика;
- встроенная панель TeamCity;
- определение текущего TeamCity origin;
- проверка TeamCity session;
- динамическая загрузка доступных мобильных проектов и их build configurations;
- классификация OS/Environment;
- ограниченный поиск до 20 последних `SUCCESS + finished` builds из всех branches;
- параллельный поиск artifacts с concurrency не более четырёх;
- фильтры Project/Platform/Environment с семантикой пустого значения `все`;
- поиск по частичному номеру задачи в branch и по точному публичному номеру build;
- локальная история запросов отдельно по режимам и TeamCity origin;
- отдельная выезжающая панель результатов с состояниями маскотов;
- множественный выбор найденных builds;
- bulk-first поиск APK/IPA с ограниченным рекурсивным fallback;
- вывод карточек только для одного найденного кандидата;
- копирование и скачивание TeamCity artifact URL;
- локальная diagnostic-консоль в diagnostic build;
- универсальный frontend-контур Telegram-действий с пустым gateway базовой сборки;
- динамическая компоновка toolbar и footer без пустых мест;
- декоративные заглушки тёмной темы и меню настроек.

## 9. Не входит в MVP

- отдельный публичный сайт;
- кнопка возле каждой строки build в TeamCity;
- автоматический выбор последнего build;
- поддержка нескольких TeamCity-инсталляций в UI;
- платные подписки и платежный провайдер;
- server API Telegram-действий;
- конкретный Telegram-контракт;
- собственное долговременное хранение artifacts;
- история отправок в Extension;
- установка IPA через TestFlight/MDM/`itms-services`;
- Firefox и Safari.

## 10. Следующие итерации

Приоритетные направления после MVP:

1. Подключаемый API gateway Telegram-действий.
2. Новые универсальные placement-слоты для Telegram-функций возле элементов TeamCity UI.
3. Поддержка других TeamCity origins и classification profiles.
4. Политики доступности и ограничений для дополнительных действий.
5. Отдельный Web UI при появлении сценариев, которым тесно внутри TeamCity.
